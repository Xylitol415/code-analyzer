# 代码分析助手：记忆与答案复用研究提示词

日期：2026-10-19。此文件用于下一步调研与方案设计，不是已经实施或验证的设计。

## 可直接使用的提示词

请基于当前 code-analyzer 仓库，研究并设计一套最小、可验证的记忆或知识复用能力。先调研和制定方案，不修改产品代码。深入解决下面的目标，不扩展成通用 Agent 记忆平台。

### 1. 目标与约束

- 系统用于让产品、研发和业务人员理解项目代码及业务逻辑。主要目标是：在答案正确、适用条件明确、代码证据仍然有效的前提下，减少重复或近似问题的总 token 消耗与端到端等待时间，提高事实和结论的一致性。
- 区分会话上下文、上下文压缩、答案缓存、可检索的项目知识，以及模型提供商的 prompt cache。它们不是同一能力，不要求全部实现。优先复用已有 pi SDK 能力。
- 网页与终端 REPL 共用核心逻辑。保持项目分析只读，新增持久数据放在应用数据目录。核心模块放到 `src/memory/`；只有确实存在独立知识发布职责时才另外建立 `src/wiki/`。
- 优先评估 zvec，避免新增复杂在线数据库服务，不调用在线 embedding 服务。可以评估本地 embedding，但必须交代模型下载、离线运行、中文与代码检索效果、冷启动及内存成本；不预设本地 embedding 一定必要。
- 长期知识和反馈必须跨重启保存。区分文件型 SQLite 与 `:memory:`；进程内缓存只作为可丢失的加速层。

### 2. 先查事实，再提出设计

检查项目实际代码和已安装 pi SDK，引用文件与行号，核实：

- 会话历史、恢复、默认及实际可配置的自动压缩、网页/REPL 共用问答入口；不要从“当前没有任何记忆”的假设出发。
- 会话队列、取消/错误/工具重试、Skills 快照、项目路径、源码版本、SSE 和历史消息 ID 的现状。
- token usage、缓存 token、首字时间和总耗时哪些已可获得，哪些缺失；缺失或费用配置为零不等于实际消耗为零。
- 当前用户身份及权限模型能否支持“多名独立用户点赞”。没有用户体系时说明匿名反馈能证明什么，不能证明什么，不以此为由顺带建设完整账户系统。

从以下材料追溯原始证据：

- 本项目源码、测试、Git 变更、已安装 SDK 的公开 API 与实现。
- 可获得的真实问答及工具轨迹：问题、业务条件、代码版本、引用、最终答复、usage、延迟和反馈。数据不存在时明确缺口，提出采样办法，不虚构使用分布或节省比例。
- zvec 官方文档、Node 绑定的发布包和源码、Mem0 的存储接口与调用链、工业界一手工程报告、公开评测的论文和数据。
- 用户给出的阿里云文章用于发现问题和术语，关键能力须回到其引用的一手来源核实。

每个关键结论标明：文档/源码已证实、设计推断、待本地验证。注明调研日期及具体版本；区分 main 分支、文档站、稳定发布包和 Python/Node 功能，不能互相替代。

### 3. 只比较与目标直接相关的路径

以当前系统为基线，比较以下增量路径；给出一条推荐的最小实现，说明什么证据会推翻推荐：

1. 带项目、源码及上下文约束的精确答案复用。
2. 本地全文/词法检索受审核的答案或事实，按需补充代码证据后生成。
3. 在第二条基础上加入本地 embedding 与 zvec 语义召回；只有收益足以覆盖新增成本才推荐。

核实 zvec Node 的全文检索/BM25、中文分词、dense/sparse、过滤、更新删除、持久化、并发读写和平台支持，尤其区分“支持向量存储”与“负责生成向量”。当前官方 Node 文档列有 FTS 接口，但是否能在本项目锁定的发布包和机器上运行，仍须单独验证。

检查 Mem0 的实际 Node/Python 实现，回答：是否已有 zvec 适配；如果没有，需要实现哪些接口、过滤及结果语义；是否仍引入 LLM 抽取、embedding 或额外进程。比较完整引入 Mem0 与借鉴其机制自行实现的必要工作，不把“理论上能替换向量库”写成“已经支持”。

### 4. 把答案何时可复用说清楚

设计“直接返回已验证答案／作为检索证据辅助生成／重新读代码分析”的决策规则。

- 明确何谓同一问题：项目、业务条件、代码状态、对话上下文、受众和输出要求可能改变答案；不能只比较问题字符串或向量距离。
- 例如“哪些条件展示弹窗”与“哪些条件不展示弹窗”、不同分支中的同一句问题、上下文中的“这个流程呢”，都应进入反例集。
- 语义相似度用于召回候选，不能单独证明答案等价。任何复用阈值均须通过独立样本校准，不随意指定 0.8/0.9。
- 定义项目身份、commit、dirty 工作区、相关配置、提示词/Skills 版本等的作用；说明生成过程中代码改变如何处理。
- 区分保守的整个源码快照约束与更精细的依赖失效。仅引用文件未改变，不足以证明调用者、配置及依赖未改变；不声称首期能完整追踪所有语义依赖。
- 规定证据出处、适用条件、审核状态、过期/冲突/撤回和重建策略。TTL 与点赞不能替代源码有效性校验。
- 直接命中缓存仍须正确写入当前会话上下文与持久历史，支持后续追问和重启恢复；不要仅向网页发一条缓存 SSE。
- 取消、失败、未完成和工具中间输出不能自动成为可信知识。只沉淀有来源的最终答案或事实，不保存凭据；知识内容不得提升 Agent 权限。

### 5. 设计反馈到知识修订的最短闭环

在现有 Tailwind 回复区域的复制按钮旁增加点赞、点踩入口，方案需要覆盖：

- 后端稳定的 answerId、答案版本及引用的知识版本；实时显示和历史恢复使用同一关联方式，不能只依赖前端临时 UUID。
- 幂等提交、赞踩互斥、修改及撤销；点踩可选择原因或补充说明，区分事实错误、过期、答非所问和表达问题。
- 反馈进入候选/复核队列。点赞提高复核优先级，经过代码证据核验后才发布；不得以点赞数直接替代真实性判断。
- 当前共享 Token 下说明匿名去重的局限；如果“多用户认可”是必要条件，列为身份能力的前置决策，不声称多个设备等于多个人。
- 点踩如何触发待复核、暂停直接复用、修订或撤回；给出最小状态流转与人工处理方式，避免搭建额外的大型后台。
- 修订后的原文、引用和索引如何同步，旧版仍可追溯；每次确认的错误转成回归样例，防止再次发布。

### 6. 给出能接到当前代码上的设计

仅为推荐路径给出：模块职责、最小数据结构、核心 TypeScript 接口草案、网页/REPL 接入点、必要 HTTP/SSE 字段，以及两条时序：

- 提问 → 有效性判断 → 复用/检索/分析 → 更新会话 → 形成候选。
- 点赞/点踩 → 人工核验 → 发布/修订/撤回 → 后续查询生效。

如果组合 SQLite 与 zvec，明确唯一事实存储与可重建索引的边界。解释 HTTP 和多个独立 REPL 进程的写入协调、索引刷新、部分失败与重启恢复，不假设进程内 Map 能解决跨进程问题。检索不可用时应能回退到现有代码分析链路，并可关闭复用重新分析。

### 7. 用实验判断收益，而不是承诺收益

提出可复现实验协议，先设计，不冒充已经完成实验：

- 数据以本项目或真实目标项目为主，标注正确结论、代码证据及哪些旧答案允许复用。包括完全重复、中文改写、代码标识符、相似但条件相反、跨项目/分支、dirty 修改、上下文追问、证据缺失、答案冲突和撤回。
- 将同一问题族放在同一数据分区；将阈值开发集与最终评测集分开，并按时间回放代码更新与知识发布，防止使用未来答案或评测答案污染索引。精确重复的预热数据与未见改写的测试数据分别说明。
- 对比当前系统、精确缓存、词法检索、可选本地向量检索；固定模型、提示词、代码快照、机器及知识初始状态，分别报告冷启动与热运行，多次测量。
- 测量正确复用率、错误复用率及其明确分母、过期答案率、事实一致性、证据支持率、检索召回率、TTFT、总延迟 P50/P95、input/output/cached token 和本地 CPU/RAM/磁盘开销。
- 总收益纳入摘要/抽取/校验/重排的 LLM 消耗、维护和重建成本；不能只展示命中请求的节省。报告重复频率达到多少时新增成本才值得。
- 正确性由固定源码、可执行行为测试和独立业务/代码维护者盲评交叉验证；LLM judge 仅辅助，不能作为唯一裁判。LongMemEval 可借鉴更新、时间与拒答测试思路，不能替代代码问答验收。
- 给出建议验收门槛及依据，区分建议目标和实测值。展示样本量及不确定性；小样本“零错误”不能外推成生产环境百分之百正确。
- 包含并发、取消、缓存命中后追问、历史恢复、删除/修订、重启与索引故障回退用例。未实际运行的检查明确列为待验证。

### 8. 交付要求

按以下顺序交付，不罗列与目标无关的框架：

1. 当前系统事实、关键误区与证据缺口。
2. 三条路径的对比和一条最小推荐路径；清楚说明先做什么、什么条件下才值得加本地向量检索。
3. 推荐方案的决策规则、数据模型、接入位置、反馈与失效流程。
4. zvec/Mem0 兼容性证据表与尚需验证的最小技术实验。
5. 可复现评测设计、验收门槛及失败后的回退办法。
6. 仅列出会改变方案选择的待确认问题；其余采用明确写出的合理假设。

引用链接靠近对应结论。不要使用厂商宣传的节省比例、数据库检索速度或通用记忆榜单，代替本项目的正确性和端到端收益证据。
